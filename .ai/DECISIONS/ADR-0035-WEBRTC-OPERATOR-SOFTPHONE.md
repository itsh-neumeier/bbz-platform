# ADR-0035: WebRTC operator softphone — the browser is a SIP endpoint, BBZ bridges it over ARI

## Status
Accepted (2026-09-08, roadmap E13-11 / #816)

## Context

Epic 13 connected BBZ to Asterisk (`telephony_sip` / ARI, ADR-0023), gave BBZ a
DB-backed gateway config (ADR-0033) and a generated ITSP trunk config
(ADR-0034). Inbound and outbound PSTN calls now reach BBZ: a trunk call lands
in `Stasis(bbz-sip, …)`, BBZ answers it over ARI, `dial` originates
`PJSIP/<dest>@<trunk>`.

**There is no second audio leg.** When BBZ "answers" a trunk call over ARI the
channel is up, but nobody is on the BBZ side — no microphone, no speaker. The
LEONET live test confirmed it: the call connects, `pjsip show channels` shows
the trunk channel in Stasis, and there is silence. The operator sits at a
browser (the web client, or — for field debugging — a phone browser); the
workstation has no hardware SIP phone and Epic 08 (kiosk) is not the only
target. The operator's own browser must become the other end of the call.

### Options for the operator audio path

- **A hardware/desktop SIP phone per workstation.** This is the Epic 12 (Cisco
  CUCM) world and a valid deployment, but it does not help a browser operator,
  a mobile debug session, or a site without Cisco. Out of scope here; not
  mutually exclusive with this ADR.
- **Server-side audio (BBZ terminates RTP itself).** BBZ would need a media
  stack (RTP, codecs, echo cancellation, jitter buffer) and a way to get that
  audio to the browser anyway — which is WebRTC. No reason to rebuild what
  Asterisk already does well.
- **The browser registers to Asterisk as a WebRTC SIP endpoint** (chosen).
  Asterisk has had a mature WebRTC endpoint (`webrtc=yes`: DTLS-SRTP, ICE,
  `rtcp_mux`, `rtp_symmetric`) and a SIP-over-WebSocket transport
  (`transport-wss`) for a decade; `chan_pjsip` bridges a WebRTC channel and a
  trunk channel like any other two channels. The browser side is a well-trodden
  path (JsSIP / SIP.js). BBZ already drives bridging over ARI.

## Decision

**Each operator gets a per-person WebRTC SIP endpoint on BBZ's Asterisk. The
browser registers to `transport-wss` with short-lived-ish per-operator
credentials that BBZ hands out over TLS. On answer/dial, BBZ's `telephony_sip`
adapter bridges the operator's WebRTC channel with the trunk channel over ARI.**

### 1 · New domain table (migration 0058) — `sip_webrtc_endpoints`

One row per operator that may take calls in the browser:

- `user_id` (PK, FK → `users.id`, CASCADE) — the endpoint is the person, not the
  workstation. Workplace-scoped endpoints (a fixed desk phone identity) are a
  possible extension when Epic 23 placement lands; not now.
- `auth_username` (unique) — the SIP username, e.g. `op-<8 hex>`. Generated by
  BBZ, not chosen, so it never collides with a trunk/number user.
- `auth_password_ciphertext` — Fernet, **same key and mechanism as ADR-0033/34**
  (`BBZ_SIP_ENCRYPTION_KEY`, `bbz_core.infra.sip_secrets`). Write-only over the
  API; a rotate generates a fresh password.
- `enabled` — master switch per operator.
- `updated_by`, timestamps.

The AOR is `max_contacts=1` / `remove_existing=yes`: one browser tab holds the
registration; a second login steals it rather than forking the call.

### 2 · Credentials are handed out, not stored client-side

`GET /api/v1/telephony/webrtc-credentials` — **session-gated**, needs
`calls.answer` or `calls.dial`. Returns, for the calling user only:

```
{ ws_url, sip_uri, auth_user, auth_password, ice_servers, expires_hint }
```

- `auth_password` is the decrypted SIP password — returned **only over this
  endpoint, only over TLS, never logged, never audited**. It is the operator's
  own credential, the same trust level as their session.
- `ws_url` / `ice_servers` come from deployment config
  (`BBZ_SIP_WEBRTC_WS_URL`, `BBZ_SIP_WEBRTC_ICE_SERVERS` — env for now, an
  admin-editable runtime setting is a clean follow-up under ADR-0031).
- No password is persisted in the browser beyond the JsSIP UA's memory; a page
  reload re-fetches.

If the calling user has no endpoint row (or it is disabled), the endpoint
returns `404` with a clear body — the frontend shows "kein Softphone
eingerichtet", not a dead state.

### 3 · Config generation — extends the ADR-0034 generator

`SipWebrtcConfigService.render_pjsip()` emits, into the same
`pjsip_bbz_*.conf` `#tryinclude` space the trunk generator uses:

- one `[transport-wss]` (`protocol=wss`, `bind=0.0.0.0:8089`,
  `cert_file`/`priv_key_file` — lab: a self-signed cert generated in the image;
  prod: a real cert, path from config, **distribution documented not
  automated**).
- per enabled operator: `[<user>]` `type=endpoint` (`webrtc=yes`, `context` a
  dead `bbz-webrtc-inert` context — the browser never dials the dialplan, BBZ
  originates to it over ARI), `[<user>-auth]` `type=auth` userpass,
  `[<user>-aor]` `type=aor` (`max_contacts=1`, `remove_existing=yes`).

The `GET …/asterisk-config?part=pjsip` response now concatenates the trunk
PJSIP and the WebRTC PJSIP. Same `no-store`, same "contains cleartext
passwords, never persisted/logged/audited" rule.

### 4 · Bridging on answer/dial — ARI, in the adapter

`telephony_sip` adapter:

- `answer(call)` — create a `mixing` bridge (ARI `POST /bridges`), add the trunk
  channel, then originate to the operator's WebRTC endpoint
  (`PJSIP/<auth_user>`) with the bridge as the continuation (`POST /channels`
  with `app=bbz-sip`, then `addChannel` on `StasisStart`). When both legs are in
  the bridge the audio path is complete.
- `dial(line, dest)` — originate the trunk leg as today; when it reaches `Up`,
  auto-bridge the operator's WebRTC channel the same way.
- Which operator? The adapter is told the answering/ dialing operator's
  `auth_user` by the call-control path (the API already knows `ctx.user_id`).
  The adapter maps `user_id → auth_user` from config it is handed at build time
  (same channel as `line_endpoints` / `line_caller_ids`).
- The mock provider does none of this — it has no bridges. This is
  `telephony_sip`-only, guarded like the existing mock/real split.

### 5 · Admin API + audit

Under `/api/v1/admin/telephony/sip`, gated `integrations.configure`:
`GET .../webrtc` (list, redacted), `PUT .../webrtc/{user_id}`
(create / enable / disable / rotate password), `DELETE .../webrtc/{user_id}`.
Every write emits one **critical** audit row —
`SIP_WEBRTC_ENDPOINT_CONFIGURED` / `SIP_WEBRTC_ENDPOINT_REMOVED` — with the
`user_id` and a redacted non-secret diff, **never** a password or ciphertext.

### 6 · Frontend

`jssip` (npm, pinned). On login, if `webrtc-credentials` returns an endpoint,
the client registers the JsSIP UA over WSS, requests `getUserMedia({audio})`
(explicit permission handling — a denial is a visible message, not a hang), and
attaches the remote stream to a hidden `<audio>`. The comms sidebar gains a
microphone-status / registration indicator and a mute toggle. `apps/bbz-kiosk`
gets the same client later (Epic 08).

## Consequences

- BBZ's Asterisk now needs port `8089/wss` reachable by operators and a TLS
  cert. The lab image self-signs; production cert distribution is documented in
  `deploy/sip/`, not automated (ADR-0019 / cert-management territory).
- `BBZ_SIP_ENCRYPTION_KEY` protects one more secret class (operator SIP
  passwords). No new key.
- One WebRTC endpoint per person, `max_contacts=1`: an operator logged in twice
  (two tabs, two devices) has the newest registration win. Multi-device ring is
  out of scope.
- The browser is now a SIP UA on BBZ's Asterisk. Its credentials are per-person
  and disclosed only to that person's authenticated session; a leaked password
  lets someone register as that operator's softphone until it is rotated /
  disabled — same blast radius as a leaked session, mitigated by the rotate/
  disable admin controls and the audit trail.
- Conference (>2 legs), call recording, and codec-selection UI are explicitly
  out of scope for E13-11.
- Hold and blind transfer over a trunk (E13-13 / #819) build on the bridge this
  ADR introduces — hold parks the operator leg and plays MoH (E13-12 / #817) to
  the trunk leg; transfer swaps a leg in the bridge.

## Alternatives considered

- **SIP.js instead of JsSIP.** Equivalent for this use; JsSIP's API is smaller
  and its `RTCSession` maps 1:1 to what we need. Either would work; not a
  decision worth re-litigating later.
- **A single shared WebRTC endpoint for all operators.** Rejected — no
  per-person audit, `max_contacts` juggling, and a shared password is a worse
  secret. Per-person is the same cost once the table exists.
- **Issue a short-lived JWT the browser presents to Asterisk instead of a SIP
  password.** Asterisk `chan_pjsip` has no first-class bearer-token auth for
  register; the community patches are non-standard. Revisit if Asterisk ships
  it. The rotate/disable controls + TLS-only disclosure are the mitigation
  until then.
- **Terminate media in BBZ (aiortc / a media server).** Rebuilds Asterisk's
  media stack in Python for no gain; the audio still has to reach the browser
  over WebRTC.
